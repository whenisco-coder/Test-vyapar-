## T0: Storage spike (Android + Cloudflare Pages)

**Goal:** prove SQLite persists reliably in Brave and Firefox on the owner's Android phone, hosted on Cloudflare Pages, and choose the library.

**Inputs:** architecture.md sections 3 and 11.

**Scope**
- Throwaway app in /spike, auto-deployed by Cloudflare Pages from the private GitHub repo (D28).
- Compare wa-sqlite (Worker + OPFS) and official sqlite-wasm (opfs-sahpool).
- For each option and each browser, test:
  1. Create a table, insert 10,000 rows, query them. Record timings.
  2. Reload: data still there.
  3. Close browser, restart phone: data still there.
  4. Installed as a PWA: same behavior.
  5. Airplane mode after first load: app opens and works.
  6. Two tabs at once: locking and writes.
  7. Result of the persistent storage request.
  8. Any special server headers needed (goal: none).
- Also record: can the page read a QR/barcode from the camera in each browser (informs D34), and does a WebRTC data channel connect between two phones on the same WiFi with QR-style signaling (informs D31).

**Out of scope:** UI design, React, migrations, real schema.

**Acceptance**
- Results table (option x browser x test) with numbers, phone model and browser versions.
- A decision entry proposed for decisions.md: library, versions, headers, limits.
- If neither option passes tests 2, 3 and 5: recommend the IndexedDB (Dexie) fallback with reasons.

## T1: Data layer

**Goal:** build the Data layer: worker, typed client, schema v1, migrations, repos.

**Inputs:** architecture.md sections 2 and 3, the T0 decision.

**Step 1 (stop for review):** docs/schema.md is provided as a draft by the owner. Review it, list any problems or missing columns in a short note (do not rewrite it wholesale), and wait for owner approval before building.

**Scope (after approval)**
- Only the [v0.1] tables in docs/schema.md, including the hook columns, with conventions on every table. Do not create [R] tables.
- Stock derived from movements; ledgers append-only; changes table written in the same transaction as every write.
- HLC (hybrid logical clock) helper stored per device.
- Migration runner: versioned, safety backup, refuses downgrade.
- Repo interfaces per entity; import restriction so UI cannot import database code.

**Out of scope:** sync transports, Tally, staff roles, UI.

**Acceptance**
- Unit tests: paise math, soft delete, changes written in-transaction, stock derived from movements, migration up and safe failure, downgrade refused.
- Test that scans the schema for autoincrement: none.
- Tables for checkpoints (D40) and the indexes listed in architecture.md section 4a exist.
- A seed script can generate 5 years of data (D41); basic query timings are recorded, and bytes per invoice (including indexes and changes) are measured and reported.
- A sync simulation harness exists as a test utility (D54): virtual devices with in-memory databases, a fake network that can drop, duplicate, reorder and delay messages, and skewed clocks. Pure HLC and merge functions have unit tests.
- Test: killing the worker mid-transaction leaves no partial invoice or movement rows.
- Rolling local snapshot function exists (daily, 7 + 4 weekly, before migrations).
- App saves a customer and a product on the owner's phone and data survives restart.

## T2: App shell, onboarding, master data

**Goal:** a usable, beautiful skeleton on T1: first-run setup plus screens for products, customers, suppliers, artisans and opening stock.

**Inputs:** architecture.md, decisions.md (D15, D23, D29, D35 to D39), T1 repos. D34 (barcode/QR) must be decided by the owner before this task starts because it affects product codes.

**Step 1 (stop for review):** write docs/design-system.md: palette tokens, type scale, spacing, the 8 most used components (button, input, list/card with photo, table, modal, bottom tab bar, empty state, toast). Wait for owner approval.

**Scope (after approval)**
- Project setup per D23. PWA install, offline caching, update prompt.
- Navigation: bottom tab bar on phone with a central "New sale" button (screen arrives in T4), sidebar on desktop.
- Language switch: English, Hindi, Gujarati from translation files.
- First-run wizard: business name (suggest Ajrakhika), GSTIN (validated), address, financial year, invoice prefix and device letter (D10), stock method (default FIFO). State code from GSTIN.
- Products: standard, variant (generate from attribute grid), unique piece; name, SKU, HSN, GST rate, unit, selling price, MRP, tax-inclusive flag, category, photo (on-device WebP compression, D39).
- Parties: customers and suppliers (B2B or B2C, GSTIN, address, state). Paste a full address block to auto-fill name, address, city, pincode, state. State auto-set from pincode or GSTIN.
- Artisans: name, village, craft, mobile, optional UPI/bank text, photo.
- Opening stock: quantity, cost and location; creates a batch and an opening movement.
- GST rules as data with price slabs (D37); a few samples labelled "verify with your CA".
- Optional starter pack as a data file: units (pcs, mtr, set, pair) and categories (ajrakh block print, bandhani, Kutchi embroidery, mirror work, Rogan art, Bhujodi weaving, leather, copper bells, home decor, kurtas, sarees, dupattas).
- Each list has search, add, edit, soft delete.
- Settings: business details, prefix, stock method, negative-stock setting (D26), persistent storage status, app version, language.

**Out of scope:** purchases, invoices, payments, login, sync.

**Acceptance**
- Works on the owner's Android phone, offline after install; data survives restart.
- 500 sellable units: search under 200 ms (test).
- GSTIN validation with tests; price-slab rule resolution with tests.
- All data access through repos (no SQL in UI).
- Hindi and Gujarati labels on all main screens; contrast and tap-target checks pass.
