# Decisions

Status: DECIDED = do not reopen. OPEN = owner or a named task will decide; stop and ask. Only the owner changes a decision.

| ID | Decision | Status | Note |
|---|---|---|---|
| D1 | Offline-first. Data stays on the device. | DECIDED | Non-goals: cloud-first SaaS, Tally replacement, native apps. |
| D2 | 3 layers: Data, Domain, UI. Each talks only to the one below. UI never touches SQL. | DECIDED | Sync and Tally are modules in Domain. |
| D3 | SQLite WASM in a Web Worker, stored in OPFS. | DECIDED | Library (wa-sqlite vs official sqlite-wasm) is OPEN until T0. Test browsers: Brave and Firefox on Android 10+. |
| D4 | If T0 fails, use IndexedDB (Dexie) behind the same repo interface. | DECIDED | Only if T0 fails. |
| D5 | UUIDv7 ids. Money as integer paise. GST rates as basis points. Soft delete. Every table has created/updated/deleted timestamps, device_id, user_id. Every write appends to the changes table. | DECIDED | Never autoincrement. |
| D6 | Stock quantity is derived from an append-only movements ledger. Locations: Own, Damaged, Returns, Amazon FBA, Consignment (artisan-owned). | DECIDED | |
| D7 | Stock valuation is FIFO by default; the method is a setting (FIFO or weighted average). Never LIFO. | DECIDED | Cost is derived by deterministic replay of movements ordered by (hlc, device_id, id), so all devices agree after sync. |
| D8 | Sync uses one change log with three transports: cloud relay, same-WiFi direct, file export/import. | DECIDED | Changed by D30/D31. Relay first, then WiFi, file is last resort. |
| D9 | Sync conflicts: ledgers are union; master data last-write-wins by (hlc, device_id); finalized documents immutable (cancel + reissue); tombstones beat older updates. | DECIDED | Unique piece sold on two devices: both invoices stay valid, piece flagged "oversold" for the owner to resolve. |
| D10 | Invoice numbers: one series per device, format like A/2627/000001 (sequence at least 6 digits). Max 16 characters (letters, digits, / and - only), consecutive within a series, reset each financial year, no gaps. Cancelled invoices keep their number and are marked cancelled. | DECIDED | Device letter is part of the prefix. Prefix is a setting. Six digits so one device can issue up to 999,999 invoices a year (4 digits would cap at 9,999). CA sign-off still advised. |
| D11 | Tally integration is file-based XML export. Order: Sales (v0.1), then Receipt, then Purchase. Live sync later via a desktop bridge. | DECIDED | Data-driven mapping; golden files from real Tally exports. |
| D12 | Login: owner and staff use a local PIN. No email accounts or OTP. | DECIDED | Changed by D32. |
| D13 | Owner + staff roles in v0.1. Owner can restrict staff per permission. | DECIDED | Changed by D30. Client-side enforcement only; stated honestly in docs. |
| D14 | Backup is encrypted on the device. v0.1: share sheet. Later: Google Drive (appdata folder). | DECIDED | |
| D15 | Hosting is Cloudflare Pages (static app + Pages Functions for the relay). PWA install + offline caching from Day 1. No special headers. | DECIDED | |
| D16 | Android first. iPhone later. | DECIDED | |
| D17 | Never use html2canvas. Use native print-to-PDF or a vector PDF library. | DECIDED | Templates are built fresh (D22). |
| D18 | One business per install. | DECIDED | |
| D19 | Zero budget. Free tiers and open source only. No paid service or new account without owner approval. | DECIDED | |
| D20 | Tests (Vitest) cover money, GST, FIFO, Tally XML and sync merge. | DECIDED | UI tests later. |
| D21 | v0.1 scope, built from scratch: T0 spike, T1 data layer, T2 app shell + onboarding + master data, T3 purchases and consignment, T4 sales invoice + print/PDF, T5 payments, dues and artisan payouts, T6 backup/restore, T6A admin lab (sandbox, dummy data, audit and trace tools), T7 Tally Sales export, T8 staff roles and PIN, T9 sync core, T10 cloud relay, T11 same-WiFi sync, T12 polish. | DECIDED | Everything else is v0.2+. Phase release: T0 to T5 first (usable invoicing), then T6 and T7, then T8 to T12. |
| D22 | Build from scratch in a new repo. Do not read or copy old app code. No data is imported; the app starts empty. | DECIDED | The old app is only a workflow and look reference. |
| D23 | UI stack: React, TypeScript, Vite, Tailwind CSS, shadcn/ui, Lucide icons. Tests: Vitest. PWA: vite-plugin-pwa (Workbox). | DECIDED | |
| D24 | Not in v0.1: courier label, combined sheet, tasks, expenses, returns UI, dashboards, WhatsApp automation, e-commerce integration, extra invoice templates, GST e-invoicing (IRN, QR, portal API; owner confirmed not in this phase), GST return filing, reverse-charge computation, Google Drive backup. | DECIDED | Barcode/QR and counter mode are OPEN (D33, D34). |
| D25 | GST rounding: tax per line rounded to paise; invoice total rounded to the nearest rupee with a round-off line. | DECIDED | |
| D26 | Negative stock is allowed with a visible warning, controlled by a setting. | DECIDED | Needed because devices can sell the same last item while offline. |
| D27 | Test data only until T6 (backup/restore) is accepted. | DECIDED | After T6, all test and dummy data lives only in the Admin Lab sandbox (D48). |
| D28 | Cloudflare Pages auto-deploys from a private GitHub repo. Agents push code only and get no tokens. | DECIDED | |
| D29 | First business is handicrafts and clothing; business name Ajrakhika. Starter pack is handicrafts and clothing. | DECIDED | |
| D30 | Sync, staff roles and PIN are in v0.1. | DECIDED | Replaces the earlier "not in v0.1" notes on D8, D9, D12, D13. |
| D31 | Transports: (a) free cloud relay on Cloudflare Pages Functions + D1; (b) same-WiFi direct via WebRTC with QR pairing; (c) file. | DECIDED | WiFi transport is best effort and must be reported as not verified until tested on real phones. |
| D32 | Workspace created by the owner device; staff join by invite QR (expires in 10 minutes, single use). All sync payloads are end-to-end encrypted; the relay stores ciphertext only. Revoke a device by rotating the workspace key. | DECIDED | No email accounts. |
| D33 | Counter mode for fast shop sales (photo tiles, cart, held bills, discount, 3-inch receipt, end-of-day cash summary). | OPEN | Owner to decide before T4. |
| D34 | Barcode/QR: scan to add to a sale and print QR labels for pieces. | OPEN | Owner to decide before T2 (affects product codes). Phone camera scanning needs a small fallback library on Firefox. |
| D35 | Product model: standard items, variant items (size, colour, fabric, print type) and unique one-off pieces. Each sellable unit has its own SKU, photo and stock. | DECIDED | |
| D36 | Artisans: purchase (you own stock, payable immediately) and consignment (artisan owns stock, payable only when sold). Append-only artisan ledger and payouts. | DECIDED | GST treatment of artisan purchases is not computed in v0.1; question for the CA. |
| D37 | GST rates are data rules keyed by HSN with optional per-piece price slabs. Seeded rates are samples, labelled "verify with your CA". | DECIDED | |
| D38 | UI languages: English, Hindi, Gujarati from translation data files. | DECIDED | |
| D39 | Photos: compressed on device to WebP (max 800px), stored in OPFS, synced as encrypted blobs with a free-tier quota guard. | DECIDED | |
| D40 | Yearly checkpoints: at each financial year end (and on demand) the app saves a snapshot of stock on hand, FIFO batch remainders, customer dues and artisan payables. Replay and balance calculations start from the latest checkpoint. Old changes and movements are kept but can be compacted into the relay snapshot. | DECIDED | Keeps costing and sync fast after years of data. Checkpoints are derived data, rebuildable from the ledgers. |
| D41 | Scale target: 100,000 orders per year (about 275 a day) across up to 10 devices, with 5 years of history. Performance test: seed 500,000 invoices-worth of data and check search under 200 ms, invoice save under 500 ms, sync of a day's changes under 10 s on the owner's phone. | DECIDED | Above this, a server database is needed (out of scope). |
| D42 | Robustness rules for 1 lakh invoices a year: (1) automatic rolling local snapshots (daily, keep last 7 plus 4 weekly) before risky actions and migrations; (2) integrity check on startup and on demand (stock vs movements, invoice totals vs lines, number gaps, orphan rows, checkpoint vs replay); (3) every multi-row write is one transaction; (4) finalized invoices and ledgers are never edited, only reversed; (5) a Health screen shows storage, last backup, last sync, pending changes and integrity result; (6) restore from the relay snapshot is supported for a lost device. | DECIDED | Relay copy is encrypted and acts as an off-device backup, not a replacement for manual backups. |
| D43 | Tally export is chunked: by month or at most 2,000 vouchers per file, with a numbered file list and a "last exported invoice" marker so re-exports skip already exported invoices unless forced. | DECIDED | Large single files are slow and hard to fix in Tally. |
| D44 | Automatic Google Drive backup moves earlier if the owner agrees (currently v0.2+). | OPEN | At this volume an off-device backup beyond the relay is advisable. Owner to decide. |
| D45 | docs/schema.md is the full target schema. v0.1 creates only the [v0.1] tables, with the hook columns (empty e-invoice and e-way bill fields, channel, location_id, credit-note fields). Tables marked [R] (tasks, approvals, returns, expenses, price lists, shipments, stock transfers, stocktakes, day close) are designed but created later by additive migrations. | DECIDED | Adding them later must not require rebuilding or renaming v0.1 tables. Does not start any D24 feature. |
| D46 | Quantities are integers in thousandths (`_milli`) so metres and kilos work without floats. Locations are rows in a `locations` table (seeded with the D6 list). Payments are allocated to invoices through `payment_allocations`. | DECIDED | |
| D47 | Accountability: every row records created_by, updated_by, device_id, hlc. Cancels, adjustments and price overrides require a reason code. Approvals and tasks (later phases) link to any record by table and id. | DECIDED | |
| D48 | Admin Lab: an owner-only area with a separate sandbox database. Dummy data, stress tests and fault tests run only there. The sandbox cannot sync, cannot write to the real database, and cannot export to Tally. A banner shows when it is active. Deleting the sandbox never touches real data. | DECIDED | Mixed demo and real data is the main risk, so a separate database is used, not a flag. |
| D49 | Dummy data generator: seeded (same seed gives identical data), runs through the same Domain services and rules as real use (so validation, numbering, audit and changes all apply), configurable volume (presets 1,000 invoices, 100,000 invoices, 5 years), and runs in the background with progress, pause and cancel. | DECIDED | |
| D50 | Every transaction is traceable: one action id per user action stored on every row it writes; audit_log has one row per action; changes carry before and after. The app has a Trace view for any record and an Explain view for derived numbers (stock, dues, payables, invoice total, FIFO cost). | DECIDED | |
| D51 | Admin Lab tools: generator, performance benchmark (D41), integrity check, reconciliation reports, audit explorer (filter by user, device, action, date, record; CSV export with UTF-8 BOM), rebuild of checkpoints and caches, and fault injection (kill mid-write, duplicate and out-of-order sync delivery, clock skew). Every admin action is itself audited. | DECIDED | Sync fault tests arrive with T9. |
| D52 | Admin access: owner only. Before staff PINs exist (T8) it needs a typed confirmation phrase; after T8 it needs PIN re-entry. Staff never see it. | DECIDED | |
| D53 | Storage guard for the sandbox and the real app: (1) a storage meter in Admin and Health using `navigator.storage.estimate()`; (2) the generator shows an estimated size first and refuses to start if it would use more than 60% of free quota; (3) the generator builds data one financial year at a time, creates a checkpoint after each year and archives or prunes the old year's `changes` and audit rows, exactly as the real app will (D40); (4) a "lean mode" skips `changes` payload copies for load-only tests; (5) the real app prunes `changes` rows that every registered device has acknowledged and a checkpoint covers; (6) one-click delete of the sandbox. | DECIDED | Rough estimate to be measured in T1: 5 to 10 KB per invoice including indexes, so 100,000 invoices is about 0.5 to 1 GB. |
| D54 | Sync fault tests are built before the sync engine: a simulation harness (virtual devices with their own in-memory databases, a fake network that can drop, duplicate, reorder and delay messages, and skewed clocks) is built in T1 as a test utility. Pure merge and HLC logic is tested from T1. The full fault suite is a T9 acceptance item and runs with `npm test`. The Admin Lab (T6A) shows the fault tests as "available after T9". | DECIDED | You cannot test an engine that does not exist, but the harness and the pure rules can come first. |
| D55 | Security baseline is docs/security.md. Audit log rows are hash-chained per device (prev_hash, hash) and the integrity check verifies the chain. Admin Lab and security tests are part of acceptance for T6 to T10. | DECIDED | Hash chain detects casual tampering only; limits are stated in security.md. |
| D56 | Operations docs: docs/runbook.md (owner routines), docs/deployment.md (GitHub, Cloudflare, D1), docs/testing.md, docs/ca-questions.md, docs/design-brief.md, docs/roadmap.md, docs/glossary.md. | DECIDED | The T2 agent turns design-brief.md into design-system.md for owner approval. |
